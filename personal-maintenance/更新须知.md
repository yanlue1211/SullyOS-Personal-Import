## 二、开发优先级与禁止触碰的边界

**总体顺序：保护用户数据与原生记忆系统 ＞ 尊重原作者架构 ＞ 保留全部个人功能 ＞ 版本与部署准确 ＞ 稳定兼容 ＞ 自由创新。**

1. **记忆系统保护。** 不擅自修改原作者记忆提取、总结、召回、权重、盒子等核心算法。新增功能接入现有聊天上下文和记忆提取入口，**不另建平行记忆体系**；允许经过兼容核对后同步作者正式发布的记忆修复。改动相关代码前阅读 [记忆系统文档](../docs/memory-system-overview.md)。
2. **尊重原生架构。** 优先独立模块、组件、适配层和最小修改，便于同步作者后续更新。作者更新原则上持续融合；与个人定制冲突时理解双方逻辑后融合，而非直接覆盖、简单丢弃。**不擅改 Lite 的个人功能。**
3. **现有功能不可回退。** 新功能、Bug 修复、上游同步均须覆盖聊天、通话、音乐、语音、图片、相册、上下文、记忆、缓存、存储及备份回归。格外检查异步请求、状态同步、定时任务、事件监听、重复 API 和跨组件共享资源。
4. **先核实版本再写代码。** 查正式网页 HEAD、最新成功 Pages SHA、用户手机版本、Worker/APK 版本、其他窗口最新提交和 PR。分支可能差几百/千条提交；不得拿旧分支覆盖个人功能，重要改动保留 Git 记录与回退路径。
5. **谨慎融合，不重复造轮子。** 合并前做逐文件/逐功能差异审查：明确哪些已进入正式版、哪些独立增量尚缺、哪些为废弃实验；不直接批量合并或删除旧分支。未经明确允许不做被用户拒绝的大型架构改造。
6. **数据、隐私和费用安全。** 不擅删角色、聊天、记忆、相册、收藏及有效素材，不执行高风险数据库迁移；垃圾清理须复核全部共享引用。完整/纯文字/媒体备份要兼容。避免不必要的付费模型测试，独立 API 失败不得擅自回退昂贵主模型。Cookie、Key、Token、备份明文不得进公开代码、PR 日志。
7. **授权与风险。** 用户已授权日常读取 GitHub、修改、建分支、提交、PR、测试、修复、正常部署，**不必每步反复询问**。涉及不可逆删除、损失数据、覆盖别人的工作、大迁移、重大风险或用户明确暂缓时先确认。真实部署/验证结论如实汇报。
8. **界面与创新。** UI 精致、协调、移动端优先；配色浅绿色优先、其次浅蓝色，但服从 App 原有主题。避免为改而改；欢迎主动提出创意与不同意见，但以实用、稳定、体验为先。

**角色可读卡片规则：**所有进入私聊、角色上下文或记忆提取的写歌/演唱/游戏/造物/活动完成卡，正常描述角色完成了什么，不向角色解释后台模型、接口或生成过程，也不用刻意强调「是他自己做的」。技术过程与费用在面向用户的设置界面可以真实展示。开发前阅读 [角色卡片叙述规范](../docs/character-facing-cards.md)。

## 三、每个开发窗口的固定执行流程

1. **必读**：从正式分支读取本文件、[更新日志](./更新日志.md)、[PERSONAL_DEV_START_HERE.md](../PERSONAL_DEV_START_HERE.md) 和 [AGENTS.md](../AGENTS.md)，按模块再读专用文档。
2. **核版本**：获取正式分支实时 HEAD、最新成功 Pages SHA、手机/Worker/APK 实际版本（缺失时标「未核实」），查看当前未合并 PR、其他窗口与已有功能。必要时核查与上游的最新差异。
3. **定工作范围**：辨别当前需求属于已有、待合并、需新开发还是独立 Worker/APK；优先复用与增量融合。单个功能用基于正式 HEAD 的隔离分支，严格避免覆盖别的窗口成果。
4. **实施与验证**：最小侵入修改，跑相关单测、构建及兼容性回归；有网络、Worker 或异步链路时区分模拟测试与真实在线请求。不要做未经授权的付费测试。
5. **同步写日志（强制）**：**每次有实际代码/功能/UI/提示词/修复/上游融合/部署变更，都必须同步在 [更新日志](./更新日志.md) 新增一条记录，并让它随同一 PR/提交进入正式分支。** 别只写在聊天里。失败实验、撤回/回滚、待办也记录真实状态，**不能记录为已上线**。正式分支 PR 配有 `.github/workflows/personal-maintenance-log-check.yml` 轻量守卫：功能/部署配置文件改动未附更新日志会报告失败；纯文档修改例外。它只保护 PR 流程，直接推送或 Worker/APK 独立部署仍须主动履行记录义务。
6. **合并与部署**：审查保护项与其它提交，合并到正式分支；看对应 Pages 工作流实际结果。若涉及 Worker、APK，分别核验。部署后验证手机实际 build 标签和功能；不能测试时写「待实机验收」。成功后可追加部署 SHA/工作流链接与验收结果（文档状态补记不属于功能更新，无需无限递归补日志）。
7. **交接**：最终回复包含【起点 HEAD → 变更与 PR/commit → 测试 → 合并后 HEAD → Pages/Worker/APK 的部署状态 → 手机实际验收状态 → 尚未解决问题】。未合并分支明确写出，不模糊说「做好了」。

### 更新日志每条至少记录

- 日期（必要时标明北京时间/UTC+8）、模块、需求背景/影响范围；
- **具体更改**：做了什么，以及有什么明确不做；
- 代码分支和 PR/commit 链接（有就写）；影响的主要文件；
- **测试**：单测/构建/在线验证，成功或失败，不把 CI 当在线验证；
- **发布**：已在分支／已合并／Pages success／Worker success／手机已验收，分别记录；失败或尚未确认明确标注；
- 兼容性/数据与回退说明；遗留问题与下一步，别让下个窗口猜。

更新日志按**日期倒序**追加，新内容放顶部。老记录原则上保留历史事实，仅修正明确错误的状态并注明。**无功能变更的纯文档整理可集中记一条，不需要为补录日志再无限追加同类条目。**

## 四、跨窗口与换窗交接

- 新窗口不能假设前一个窗口「代码做了」就等于上线。先读日志、检查 PR 和实物，重复实现之前先查现有源码。
- 多窗口同时开发时，合并前再次读取正式 HEAD；存在别人新提交时应在隔离分支上**审查、融合**而非覆盖。
- 用户提出**「换窗交接」**时，完整说明本窗口的任务、已有进度、尚未完成/尚未开展的事项、过程中发现的问题、当前确切版本/分支/PR/部署状态，以及下一步计划。同步更新日志中重要未完成项。
- 任何「修好」「部署成功」陈述必须有与该目标相对应的测试和/或部署证据；后续发现说法不准确要留可追溯更正。

**目标：**在保留原作者优秀基础与所有个人成果的同时，让糯米机能长期成长、稳定运行、方便持续升级。
