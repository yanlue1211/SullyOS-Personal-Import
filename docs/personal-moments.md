# 私人朋友圈与月栖卡片更新

实现位于 `features/moments/`、`apps/MomentsApp.tsx`。核查历史见 `plans/personal-moments-v1-audit.md`。

## 使用

桌面/应用抽屉新增“朋友圈”。首次进入直接显示设置，顶端总开关默认关闭；确认开启后才展示后续设置。关闭时停止新的自动活动和朋友圈聊天注入，已有动态、浏览档案及历史聊天卡片保留。

启用要参与的角色后，user 自动与他们互为好友。角色之间在“好友关系”手动双向配置；不读取哔哔关注、联系人或关系网来猜测关系。九人关系可以按六人互加、A/B 各与六人互加、C 只与 A/D 互加配置；user 与九人均为好友。A/B 不互加，D 为六人之一。测试使用这个确切关系图，未猜测实际角色身份。

“由 TA 决定”使用一次模型请求，提供人设、可读聊天范围、记忆、世界书、日程及本人朋友圈历史。评估返回发布、浏览、互动及休息习惯，展示建议后由用户确认应用；普通保存不调用模型。后续刷新不会自动覆盖现有配置。

## 频率与预算

发布、浏览和互动是独立倾向，可以不爱发但爱刷。参考发布频率：爱发每周5～7条，普通2～3条，少发每月2～4条。参考浏览机会为每日3/2/1次。九人按三位积极、四位普通、两位较少估算每日约19次常规机会，加少量弹性机会，默认参考目标21、硬上限30；模型不需要填满分组人数或凑足请求/发帖数量。

| 倾向 | 点赞参考 | 主动评论参考 | 明确收到回复后的回应 |
|---|---|---|---|
| 积极 | 65%～85% | 35%～55% | 90%～98% |
| 普通 | 45%～65% | 20%～35% | 90%～98% |
| 较少 | 20%～40% | 10%～20% | 90%～98% |

概率提供给角色作为稳定习惯，程序不代角色抽签执行互动。参考目标达到后将剩余额度保留给明确待回应的交流，所有自动尝试仍受硬上限控制。已发送但失败、截断或格式错误的请求计入尝试次数；发出前失败不计为模型调用。手动社交请求、习惯评估和用户媒体识别单列，不挤占自动上限。

每次活动只调用一个角色的模型，一次可处理少量有权限的动态。发表新帖只创建待浏览事件，不生成配套评论。角色自己的评论不再给本人新增“待浏览”事件。没有内容、没有发布机会时本地跳过。回复可以由第三位好友发起，前提是能看见动态和被回复评论。

同一根评论的整个话题最多6条角色回复，不按参与者分别重置额度；已有3条回复后提示自然收束，不引入新问题。用户仍可手动发言或开启新的根话题。

## 休息时段与深夜例外

首次评估包含通常不发布的休息开始/结束小时，按角色时区解释，可以跨午夜。规律作息和夜猫子可以得到不同结果；开始与结束相同表示没有固定休息时段。浏览常见时段与发布休息时段分别配置。

每晚最多一次例外机会：通常晚睡概率参考1%～8%；确实有近期双方夜聊时，有感而发机会参考20%～50%。程序每晚分别判断一次，不每五分钟重复抽签。深夜例外受每日额度、至少四小时发布冷却和主题防重限制；机会不等于必须发帖，不次日补发。

## 权限和持久化

新数据使用主 IndexedDB v79 的独立 `moments_records` 命名空间及类型/角色/时间/待办/日期索引，不经过原哔哔公开化迁移。每条动态有全部好友、部分好友、不给谁看、仅自己四种独立权限。

读取先投影权限，再给 UI/模型/检索/事件卡。发布者能看全部互动，本人能看自己的互动，其他人只看共同好友互动；隐藏父评论的回复一起隐藏，避免名称和引用泄漏。提交时再次检查最新角色、开关、权限版本及动态修订。多标签页共用数据库租约，迟到响应和重复回包不能再次落库。

五分钟巡检仅在页面可见、解锁、功能开启时挂载。恢复后重新排正常机会，不补发离线轮数。每个 tick 至多一个模型请求，浏览候选最多五条、候选材料最多约16000字符，评论和媒体描述做有来源ID的节选；角色原有上下文按正常可读范围完整复用，不额外设置整轮输入 Token 上限，也不要求为朋友圈缩小聊天范围。输出 Token 跟随角色独立 API 的设置，未指定时继承全局配置；仅新增的朋友圈候选材料分批限量。

真实图片最多九张或单个视频，复用压缩、Blob 存储及最多六帧视频抽取。识别一次后按媒体内容缓存；视频只理解给出的画面，不声称听到声音。虚拟媒体用描述作为角色世界中的实际照片/视频理解，点击查看文字。

## 聊天和记忆

实际浏览保存档案，即使没有点赞/评论也保存。新评论是独立增量事件，不重置原帖浏览状态。最近三天见闻保存为稳定文本，使用绝对时间、通常不超过约4500字符；无新社交事件的普通聊天复用原文本，不重新摘要/排序或生成相对时间。到期维护和权限收紧可以更新一次快照。

明确要求角色查看时，在实际本地聊天生成前读取有权限内容并记录浏览，复用主聊天请求，不追加社交模型请求。单纯提及朋友圈只检索已浏览材料，不偷偷带入后来新增的评论。连续追问仅沿用上一段可靠的朋友圈话题和有效期；对象不明时给角色澄清提示。默认关闭状态的聊天不读取朋友圈数据库。

角色发布、评论、回复，以及实际读到别人对自己的评论/回复，按同一轮活动合并为一张折叠 `moments_card` 写入共享消息库；重要事件合并在同一张卡片中，不重复投递。普通浏览、点赞和空巡检不写卡片。卡片包含动态ID、绝对时间、实际正文与可读互动，不把未提交的评论塞进记忆。程序直接使用本轮成功保存的活动结果，不新增模型调用，也不提高记忆重要性。多动态卡片按来源分段保存，用户真实删除或编辑仅更新对应段，不影响其他经历与已有长期记忆。投递幂等，提交后触发现有聊天刷新和记忆缓冲检查；自动提取与手动归档沿用 `messageFormat` 和原有阈值/水位，不重写记忆算法。

完整导出、流式分片导出及导入均包含朋友圈记录；完整包通过现有 Blob 旁路携带像素。旧完整包没有该字段时初始化为关闭的空朋友圈。恢复结束旧请求租约，不重放旧模型调用。媒体专用备份不替换朋友圈文字和关系；本版不提供单独朋友圈媒体补丁导出。

## 哔哔公众人物模式

在哔哔设置中按角色开启，并按具体账号管理适合公开互动的同行许可。需要“明确许可 + 角色已确认账号身份”同时满足；user、普通粉丝、未知身份和未许可小号不能获得主动互动。

共享落库入口检查评论/转发、明确回复、即时接话的隐式回复目标及附带关注动作，所有主/副模型、刷新和即时评论路径都经过该门禁。外观草稿不会覆盖后来更新的公众人物配置。已有代码未提供的点赞/私信不另造写操作。提示词限定公开平台表达，私人朋友圈好友不会自动成为公开互动许可。

## 月栖与卡片长按

月栖实际请求新增听者定位：正在直接与 user 本人讲话，对听者使用“你”或双方熟悉称呼；不把当前听者当作第三人“她/他/TA”旁述。故事中的其他人物保持正常叙述。

月栖卡片取消自己的“长按展开”拦截，接入聊天原有消息菜单，可长按后选择“删除消息”，多选时也有选择入口。短按按钮仍可展开摘要/查看记录；长按松手不误触跳转，滑动和卸载取消未完成的长按。原有外观保留，其他卡片的共享菜单一起回归。

月栖新增正文清理：去掉误输出的时间头、月栖场景头、系统提示和语音包装标签；历史文字展示也清理。MiniMax 合成前仅在换行段落边界加入内置 `<#0.6#>`，不在段内句子间补标记，不展示给用户；这一路跳过经典模式的逐标点补停顿。已合成音频不能靠文字清理重写，需要重新合成才能去掉已读入音频的提示。

## 验证与发布状态

本地行为/集成测试和生产构建见本次工作记录。测试只使用合成存档与受控模型响应，不调用用户真实模型。提供 `test/fixtures/moments.html` 以及 `scripts/test-moments-browser.mjs`，用于390/320px、发布、虚拟媒体、评论、持久化、休息设置和零模型调用的浏览器验收。

当前宿主限制浏览器进程所需的系统调用，本地 Chromium 无法启动；已准备 `.github/workflows/moments-verify.yml` 在 Ubuntu24.04 进行浏览器验收并上传截图。GitHub 源码推送被自动审批拦截，等待用户明确确认上传目标；未重试上传，也未合并或部署。原 PR #37 当前远程内容仍为第一阶段核查文档。

聊天查询只检查最新 user 消息，角色提及不触发。作者全名或明确称呼（小贺、丁哥、源源等）加朋友圈才按作者最近50条读取，过滤权限及实际浏览状态后按时间取最多5条，不做关键词语义搜索。单字短名若只对应唯一长名，则按同一人物的不同账号合并匹配，每个账号独立检查权限；同称呼对应不同人物时询问。普通文字中的单字不作为简称。结果绑定当前 user 消息ID，新消息不再携带旧查询块；紧接着的明确单动态追问沿用既有话题。三天近期见闻与临时查询独立，接受卡片与见闻少量重复。未读、没查到或不能确认时应表达不确定，不编写后续、不把刚翻到说成一直记得。

歌曲识别的关联回归：网易云、导入直链及本地音频统一按文件头识别真实格式，不依赖扩展名/服务器 MIME；维持原 input_audio 请求。下载到网页/错误内容时中止；模型明确未收到音频的结果不保存为分析、旧失败分析不复用。实测示例 tonghuashun.mp3 为 Ogg，9,355,095 字节，已验证编码到实际请求出口的数据往返一致；不代表已验证用户私有中转的真实模型响应。

## 评论管理与互动回执

评论正文使用完整列宽，时间戳独立置于右下方；无删除×，短按仍回复，长按/右键打开管理菜单。滑动和取消触摸取消长按，松手不误触回复。user可修改或真实删除所有动态下的评论；char仅可普通删除本人评论（活动决策delete_comment），无修改或真实删除权限。删除父评论连同回复链处理。

普通删除保留评论墓碑及已浏览档案/卡片；新浏览者、界面和模型候选不再看到。真实删除/修改在同一事务更新原记录、实际看过者的档案、关联活动卡片及近期见闻，保留未涉及的动态段及未知评论边界，不改长期记忆。新卡片附可重建的已读投影；旧文本卡片兼容替换对应评论。

新点赞不再进入待浏览事件队列，也不触发新的互动考虑；旧版本遗留的点赞待办由本地巡检结束。点赞在之后实际浏览动态时正常可见。角色实际浏览后，见闻记录已看到的点赞及针对自己的新评论/回复，并按成功执行的操作记录本轮是否新增评论/回复；不推测心理，不把尚未浏览当已知。评论/回复回执进入活动卡片，点赞单独不出卡。

## 自动评论的回复对象校验

模型每条评论明确给出recipientId；直接对帖主说时replyTo为空，接某条可见评论时replyTo与该评论作者绑定。候选同时给出人物名字、角色ID和评论ID对应表。程序校验recipientId与实际指向一致；开头明确称呼另一位已知人物时拦截，正文中途提及、引用第三人不据此改挂。保留第三位好友接话及分身简称规则，不靠昵称自动重写对象、不额外调用模型重试。旧评论不批量推断或移动，避免改变原有经历。

## 2026-11-02 社交习惯与增量接话

首次看动态评论帖主仍使用原 commentChance（积极35～55%、普通20～35%、较少10～20%）。新增 joinChance 单独表示与自己无关的新评论的主动接话倾向，参考积极8～15%、普通3～8%、较少1～3%。一次浏览整体判断参与意愿，不对每条评论重复抽签；可回应多条不同的新评论，每个目标本轮最多回应一次。

明确回复自己的新评论使用高 replyChance，无论动态属于谁；自己动态下直接评论自己的根评论也按此处理。结束语、表情、无新信息不要求继续回应。活动输入区分首次浏览、新评论ID与明确对自己说的评论ID；已读动态禁止重新发根评论或回复旧评论。原有同根话题3条回复后提示收束、最多6条角色回复的限制保留。新增点赞不会排活动，已有点赞待办不调用模型。

老配置和旧备份无需重新评估：保留原 commentChance/replyChance，缺少 joinChance 时按既有互动性格使用12%/5%/2%默认倾向；设置可调整，重新评估时单独生成并在建议中展示。这些数值仍为模型性格倾向，不是程序硬抽签。未修改原生记忆逻辑。


## 2026-11-09 自主评论、自然散场与浏览器后台活动

此节取代上面历史记录中“首次评论／跨楼／回复概率由程序硬抽签”的描述。朋友圈位于 `features/moments/`，与作者原生公开「哔哔」`friendFeed` 独立。

- **角色自主决定有没有兴趣：** `commentChance`、`joinChance`、`replyChance` 保留为模型可参考的社交习惯，而不是概率准入门槛。第一次真正浏览帖子时，每个好友都可以自行判断是否发表根评论；已经浏览过的帖子不允许重新追加旧根评论。遇到新评论时，角色可结合人设、记忆、关系和作品背景，自行决定是否接话。例如别人提到自己的歌曲，哪怕没直接写自己的名字，也不因随机数被挡住。
- **防接龙仍由程序执行：** 只能回复本次新看到的评论，不重放已读旧评论；同一根话题的角色自动回复链最多深入 3 层，同一根话题每个角色最多自动回复 2 次，原有每根话题最多 6 条回复仍生效。每个非帖主同帖最多 3 条自动评论、帖主最多 10 条；一轮非帖主对同帖最多发 1 条、帖主最多 4 条。自动普通互动整帖最多 16 条，防止多楼层轮流接龙。用户本人手动评论不受以上自动互动数量限制。
- **用户回应保留小额空间：** 整帖已有 16 条自动评论后，允许继续响应“用户直接评论帖主”或“用户回复某角色本人评论”的新事件，最多再提供 4 条自动回复；仍须遵守深度、单角色与同话题上限，不能无限续话。无特别高优先级的普通互动到达 16 条后自然停止。该保留额度不单独唤起额外模型请求。
- **后台仍活着则可活动：** `MomentsRuntime` 不再以 `document.hidden` 为停止条件。朋友圈总开关关闭、糯米机内部锁定或组件卸载时仍停用/取消当前活动。网页在后台运行时维持原来的约五分钟单计时器巡检，遇到切换前后台不重置到下一轮、不会同时发起两次活动；浏览器重新唤醒时逾期巡检只执行一次，不补发离线时段的轮数。移动系统对后台计时器有节流甚至冻结的权限，页面被系统杀死后无法在纯网页中持续运行；实际后台执行频率取决于浏览器和系统的限制。
- **隐私、数据与费用：** 仅改原私人朋友圈的机会判断、提交校验与巡检组件；不修改原生记忆系统、作者的公开哔哔、角色数据或现存朋友圈记录。没有新增独立识别兴趣的模型请求，仍受原来的自动日预算、权限与租约限制。用户打算自行清空朋友圈，程序不自动删除任何历史记录。


## 2026-11-10 朋友圈回复过于密集的定向收束

根据一次实际观察：一条朋友圈上午发布、当晚已有 5 条首次留言及 9 条自动回复（共 14 条），证明“总上限16条”和“深度3层”虽可防止无限接龙，仍不足以避免每个人反复回应的过度热闹。

**只收紧自动续话，不恢复首次参与的硬抽签：**
- 任意好友第一次看到帖子仍由自己的模型依据兴趣决定是否评论，不规定最多几个参与者，也无需额外 API 进行相关性识别。
- 帖主每轮同帖最多新回复2条（原为4条），其他角色保持每轮同帖最多1条。
- 普通（非用户发起）同一根话题最多2条角色自动回复；整条帖子的“回复别人自动回复的进一步接话”最多2条。这样保留“先评论、帖主回应、偶尔继续聊一句”，却不允许所有人持续循环。用户明确对角色的新评论仍走已有独立有限回复通道，守护用户互动。
- 整帖自动评论总预算16、角色每帖预算、回复深度3及原有每根6条回复限制均保留。不会删除旧数据，也不改变作者原生公开「哔哔」、原生记忆、媒体和备份。

## 私聊活动记录的回复链（2026-11-11）

新活动记录仅保存朋友圈原文及本次相关评论的祖先链。例如F回复A给E的回复时，记录为原文 → E评论 → A回复E → F回复A，不携带B/C/D等无关分支。同一轮同一帖的多条链取并集，公共祖先和原文只写一次。直接评论仅带本次评论；发布仅带原文。结构化 metadata 中的评论也同步过滤，不仅精简显示文本。

活动是否进私聊仍沿用原触发：发布、实际评论/回复、首次读到明确给自己的评论/回复，以及原有重要见闻；浏览和点赞本身不新增活动卡。快照仍保留符合权限的近期完整见闻，不改变3天、30条、4,500字符规则。不迁移或重写旧活动记录；旧格式继续可读，用户显式修订评论时兼容旧记录，新格式修订后仍保持链路范围。去重、可见权限、记忆入口和记忆重要性规则保持原实现，不追加模型调用。

## 无新互动时的卡片门禁（2026-11-14）

修复模型返回 `important` 可把普通浏览／点赞单独提升为私聊活动卡的旁路。重要性说明只能合并到本轮真实新发布、成功评论／回复或首次读到针对自己的新评论所产生的对应动态段；没有这些事件就不写卡。浏览档案和快照照常保留，不额外调用模型，不改记忆提取核心，也不删除已有聊天卡或长期记忆。

同次修复浏览节选覆盖已读状态的问题：`Seen.readCommentIds` 以可选字段累计真正读过的评论编号，活动候选、首次收到判断及聊天明确查看共用这组编号；节选变短不会让读过的评论再次变成“新评论”。仅用于去重，不向模型补入未读正文。旧档案缺字段时兼容读取已有投影，备份保留并校验新字段，无数据库版本迁移、不删历史。已丢失的旧编号不能凭空补造，修复保护之后的已读记录。
