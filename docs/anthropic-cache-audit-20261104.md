优先级：数据完整性 > 角色设定正确性 > 现有缓存稳定性 > 跨角色收益。

## 当前真实请求排列

原生出口（utils/anthropicApi.ts）：`tools → system → messages`。

| 层 | 真实内容/顺序 | 稳定性 |
| --- | --- | --- |
| tools | 按调用方提供顺序转换 function 工具定义 | 清单/描述/参数/顺序相同时稳定；角色 MCP 配置可能不同 |
| system 开头 | 可选心声提醒；表达规则、来电引导 | 受模式与角色开关影响 |
| 核心上下文 | 角色设定前世界书 → 角色身份/备注/核心设定 → 自我领悟 → char.worldview → 角色设定后/示例前/示例后世界书 | 人设稳定；世界书受触发、概率、宏与顺序影响 |
| 核心上下文续 | 用户画像 → 家园/宠物 → 用户印象 → 宫殿门牌底色 → 长期/月度与激活详细记忆 → 作者注释顶部/底部世界书 → 通用表达规则等 | 非逐轮召回；数据发生更新时前缀也会改变 |
| 稳定块后续 | 各功能能力规则、虚拟媒体/心声/状态规则、朋友圈稳定部分、输出样式、真实听歌说明、MCP 说明等（按开关） | 配置相关，不能假设跨角色一致 |
| system 末尾 | 原生转换器解释 system-reminder 的固定说明（有尾部提醒时） | 有无提醒会改变该块 |
| messages 前段 | 清洗后的历史；指定深度世界书保留其原角色和深度 | 历史增长；深度条目可能变化 |
| messages 尾段 | 原易变 system 转成原位置的 user/system-reminder：当前时间、宫殿召回、情绪、实时天气新闻/位置、日程/音乐、群背景、造物间/购物/协同/本轮策略、recency 钢印、SAR、其他尾部提醒 | 逐轮变化；本次不更改任何正文或转换语义 |
| 工具续答 | 原生签名思考、工具调用与结果 | 原样保留；若已经跨过动态提醒，不作为新缓存候选 |

实际模块细节见 `ContextBuilder.buildCoreContextFromSections`、`ChatPrompts.buildSystemPromptParts`、`buildChatRequestPayload`。自然风格关闭或 App 专用入口使用对应分支，并非所有请求都有上述全部字段。开发调试的 system 合并开关会将动态段移回顶部；开启时无法得到相同的稳定历史边界，本次不擅自改变该调试功能。

## 断点与已确认故障

最多四个，全部 `{type:'ephemeral'}`（默认 5 分钟）：

1. 有工具时，在最后一个工具定义。
2. 有 system 时，在最后一个 system 文本块。
3. 第一条历史后 system/developer 之前，可标记历史块达到八个时，放在索引 `floor((n-1)*0.7)`。
4. 同一区域最后一个可标记历史块。

thinking/redacted_thinking 不直接标记。缓存匹配包含断点之前所有工具/系统/消息；不是单独缓存最后一个块。短于模型最低阈值、模型/渠道或工作空间不同、前缀变化、TTL 超期均不能保证命中。这里只对明确选择 Anthropic 原生 Messages 的出口生效；OpenAI 兼容渠道的缓存由渠道决定。

故障：旧代码用 `startsWith('<system-reminder>\\n')` 检查字面反斜杠+n，而转换器生成的是真实换行，因此扫描越过动态召回，在其后继续设置断点。修复改成按原始消息结构收集候选，不匹配正文字符串，普通聊天引用同名标签也不会截断缓存。

本地修改前后对照（合成请求，非真实 API 用量）：

| --- | --- | --- |
| 1 | 动态提醒后的工具结果 | 历史 0 |
| 8 | 历史 7、动态提醒后的工具结果 | 历史 4、历史 7 |
| 30 | 历史 23、动态提醒后的工具结果 | 历史 20、历史 29 |

每组更换召回 A/B 后，新断点都不包含召回；去除 `cache_control` 后，新旧完整请求深度相等。这证明此次修复不改变模型可见正文、顺序或工具签名，不能替代真实模型的表达回归和计费验证。既有历史 checkpoint 策略保留，未保证每次请求都零写入。

## 跨 Char 结论与备份边界

当前稳定 system 是大文本块，尚没有共同世界书内部的独立共享断点。大部分世界书默认在角色身份之后；即使前部文本相同，文本块内部也不能作为显式断点。跨 Char 长世界书复用尚未实现。

需要先核对真实备份：是否均常驻、顺序/触发一致、展开后无 `{{char}}` 差异、共同前缀无角色信息、工具清单完全相同。关键词/概率/深度/角色类型不可丢失，不能简单把专属书搬进 worldview。原生已有 `char.worldview`，位于人设和自我领悟之后、一般世界书之前；本次不新增字段、不迁移数据。

发现最新私有备份 Release：`sully-backup-v2-1793751573564`，四个 zip 分卷与事务 manifest，原始 Release 未改动。连接器可读元数据，但不支持二进制附件下载；尝试读取 manifest 下载 URL 返回 404。尚未读取备份正文，因此不能提供实际 A/B/C 世界书清单、导入完整性结论或优化备份。取得原始四个分卷后，先校验摘要、拼接方式和原版导入结构，再做逐角色对照。当前选择仅修程序缓存边界，备份保持原样。

## 费用和实测要求

原生 usage：`input_tokens` 是普通未缓存输入，读取与创建单列；归一化的 `prompt_tokens` 为三者相加，不能把它再当普通输入重复计费。

实际输入费用应按渠道对应模型单价计算：`input_tokens * 普通单价 + cache_read_input_tokens * 读取单价 + cache_creation_input_tokens * 写入单价`。官方默认五分钟写入为普通输入的 1.25 倍；读取倍率依模型，第三方渠道以实际账单为准。

尚无实际调用凭据/可读的本轮生产 usage，未执行付费模型请求，未声称省钱百分比或缓存命中率提升。待实测：

- 同 Char 连续至少两轮，保存原生 usage 与完整脱敏请求；比较原有稳定前缀和加权费用。
- 同历史、不同召回，确认召回正文存在且断点在其前，分别记录三类输入 token。
- A → B（相同模型/渠道/工作空间、TTL 内），仅在共同前缀真实完全一致后验证读取；未命中不得归因为“已共享”。
- 专属设定按角色核对，备份若修改则核对所有非世界书数据字节/语义摘要、数量及原版导入流程。
